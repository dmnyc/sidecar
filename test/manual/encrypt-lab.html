Sidecar encrypt lab

Each button makes one window.nostr call and prints what came back. Watch the approval card, not this page: the thing under test is whether it tells you what is being sealed.

not connected

1. Encrypt to yourself (NIP-44)

What an app does to store its own settings, and the case #305 is about. Expect the plaintext on the card, with a padlock.

2. Encrypt to someone else (NIP-44)

What a DM client does. Expect the message text, and a different recipient in the To row. Sealing to a stranger and sealing to yourself are different decisions, so both rows have to be readable.

3. Legacy NIP-04

Same card, NIP-04 in the method line.

4. A very long plaintext

Expect it clamped to about 220 characters with an ellipsis, and the Approve button still on screen. Page-written text must never be able to push the buttons off the card.

5. Plaintext that is trying something

Markup, a fake padlock row, and an RTL override. Expect all of it as literal text. If any of it renders as markup, or the fake row is indistinguishable from a real one, that is a finding.

6. The two-prompt sequence from the issue

Encrypt a settings blob, then sign the kind 30078 event that carries it. Expect two cards: the first shows the plaintext, the second shows the ciphertext — which is exactly the gap #305 describes, and what a follow-up would close by carrying the plaintext into the signing card too. Nothing is published.

7. Decrypt it again

Round-trips whatever case 1 produced. Expect the decrypt card, which still shows only who it is from — unchanged by this work, and the other half of what the issue asks for.

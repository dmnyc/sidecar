# lightning.pub / ShockWallet — integrating with Sidecar's wallet

*Assessed 2026-10-26. An exploration on `docs/lightning-pub-shockwallet`: no product
code changed. Sources are the repos and specs as they stand today, plus Sidecar's own
code; every Sidecar claim below is checkable in the tree.*

## What each side is

**Sidecar's wallet is NWC, plus CLINK-as-payer.** One NIP-47 connection per Nostr
account, encrypted at rest beside the nsec (`keystore.js`, `sidecar_nwc_connections`),
spoken to by `nwc-client.js` (get_info, get_balance, pay_invoice, pay_keysend,
make_invoice, list_transactions, lookup_invoice, 23196 notifications) and, for pages,
by the WebLN translation in `background.js`. Separately, `clink.js` implements the
**payer side of CLINK Offers**: decode a `noffer1…`, ask for an invoice over kind
21001 on the offer's own relay, pay it from whatever NWC wallet is connected. That
shipped in #359, and clinkme.dev already lists Sidecar — the only signer listed,
"pays offers from a profile."

**lightning.pub does not speak NWC at all.** The repo's README and issue tracker
contain no NIP-47 surface we could find (an issue search for `nwc` returns nothing;
it is not in the awesome-nwc catalog either). What a Pub offers instead:

- A **native nostr RPC** over kind **21000**, NIP-44 **v1** encrypted
  (`src/services/nostr/handler.ts` decrypts 21000 with v1 and the CLINK kinds with
  v2), authenticating the caller by signing key across Admin/App/Guest/User levels —
  a hundred-plus autogenerated methods covering channels, accounts, payments, offers
  and LNURL. This is the protocol ShockWallet speaks.
- **CLINK** (specs at [shocknet/CLINK](https://github.com/shocknet/CLINK), public
  domain — the NIP PR
  [nostr-protocol/nips#1529](https://github.com/nostr-protocol/nips/pull/1529) was
  closed unmerged in June 2025, which `clink.js`'s header comment still gets wrong):
  Offers 21001 (Sidecar ships this), **Debits 21002**, Manage 21003, Enroll 21004,
  Beacon 30078.
- An LNURL/Lightning-address bridge: `bridgelet`, static config — whoever runs the
  server maps `name@domain` → `clink_offer` by hand, and forwards NIP-57 zap requests
  through to the kind 21001 flow. A bridge of this kind is what hands Pub accounts
  their `@shockwallet.app` addresses.

ShockWallet today is [`shocknet/wallet2`](https://github.com/shocknet/wallet2) — a
React/Ionic PWA/Android/iOS reference client for a Pub — and it supports Debits:
recurring payments and pre-authorization for external apps that request payment.

## Where the two already meet — and where they don't

They meet on **being paid and paying Pub-hosted payees**. A noffer on a profile is
payable from Sidecar today; a `@shockwallet.app` address zaps through the ordinary
LNURL path; Sidecar's own profile editor already tells users to "Generate one with
Zeus, ShockWallet or Lightning.Pub"; the QR handoff of a `lightning:noffer1…` exists
precisely because those wallets read it.

They do not meet on **spending from a Pub in Sidecar**. A user whose sats live on a
Pub (theirs, or an Uncle Jim's) cannot connect that money to Sidecar: zaps from the
panel, the Send form, CLINK offers, WebLN sites, the pay pill, the context menu and
auto-zap all require a separate, NWC wallet. That is the integration gap; everything
below is about closing it, honestly costed against the rules in
`WALLET_BACKENDS.md`.

## Four ways to close it

### 1. lightning.pub speaks NIP-47 — upstream ask, zero Sidecar work

A compatibility shim on the Pub would make every Sidecar surface work unchanged:
paste the URI, the `getInfo` validation round-trip, balance card, transactions, the
`lookup_invoice` race in `payAndConfirm`, notifications. But ShockNet's stated
position is that CLINK succeeds NWC — they withdrew the NIP PR rather than amend
NIP-47, and the CLINK README frames NWC as a Nostr-tunnelled wallet-remote-control
API and builds CLINK beside it, not on it. **Ask once; expect no.** If it ever ships, the work is
a `wallets.js` entry and nothing else.

### 2. CLINK Debits as a second, spend-only connection type — the live candidate

The user pastes (or later scans) their `ndebit1…` from ShockWallet; Sidecar sends a
kind **21002** request — NIP-44 v2, `{bolt11, amount_sats}` to the service named in
the string — and gets `{"res":"ok","preimage":…}` or a GFY error (codes 1 denied,
2 temporary, 3 expired, 4 rate limited with `retry_after`, 5 invalid amount with
`range`, 6 invalid). This is the `ClinkSDK` shape (`newNdebitPaymentRequest`,
`newNdebitBudgetRequest`), so it is the integration ShockNet designed for exactly
this case.

First, retire the objection we already wrote down. CHANGELOG #359 says Sidecar
"makes no claim on Debits" because "an extension asleep in a side panel cannot be
awake to answer a request with a fresh invoice" — true, and it rules out Sidecar
*serving* offers or debits. The payer side of Debits is outbound, sent while the
panel is open, exactly like every NWC call Sidecar makes. Nothing about it needs
Sidecar awake.

What makes it attractive against `WALLET_BACKENDS.md`'s tests:

- **No shared secret in the pasted string.** An `ndebit` carries a service pubkey,
  a relay and a pointer id — authorization is by *signing key*. A first request from
  an unknown key prompts the user **in ShockWallet**, which can grant a standing
  rule (`frequency: {number, unit}` — the DebitRule/FrequencyRule budgets already in
  the Pub's RPC). This is the file's "fully app-initiated handshake — Sidecar
  generates a keypair, the user approves in their wallet, no copy-paste at all …
  remains the ideal," arrived at without an HTTP token exchange.
- **No new dependency, no funds held, Firefox identical.** The exchange mirrors
  `clink.js`: bech32/TLV decode already exists (add the `ndebit` HRP and TLV 3,
  the single-use `k1` session id), kind 21002 is the same
  encrypt→subscribe-first→publish dance as 21001, and `test/clink-pay.test.js`'s
  lift-and-run pattern applies unchanged. Likely a few hundred lines against
  protocol code Sidecar already owns.
- **The approval machinery carries over whole.** Budgets (`wallet-budgets.js`),
  large-send gating, the pay card, pay-from-account — all wallet-agnostic today,
  because they sit above `pay_invoice`.

The signing-key choice is a real decision, not a detail:

- **Sign with the user's identity key** and ShockWallet shows the user their own
  npub asking to pay — but spend authority rides on the nsec; a leaked key spends up
  to whatever the wallet-side rule allows.
- **Generate a per-install app key** (the SDK's own `generateSecretKey()` model) and
  the blast radius is that key alone; ShockWallet shows "an app key," revocable
  without touching the account.

Recommendation: the per-install key, stored exactly where the NWC string is stored,
under the same DEK and in the same vault export. Note the spec's owner-key rule —
direct operations signed by the account owner key MUST be auto-allowed — which is
what makes option 4 frictionless, and is exactly the property that makes the
identity key the wrong one to volunteer here.

What Debits deliberately does **not** provide — CLINK has no account query in any
of its five specs, and the Beacon spec is explicit that it carries "no per-account
pointers, balances, or wallet RPC" — and what that costs Sidecar:

| NWC capability | Debits equivalent | Consequence |
|---|---|---|
| `get_balance` | none | No balance card; WebLN `getBalance` errors; `SIDECAR_HAS_NWC` gating needs a "spend-only" state |
| `make_invoice` | none | Receive can't mint; the profile's noffer/lud16 QR — already built — becomes the receive story |
| `list_transactions` | none | History is Sidecar's own payment log only |
| `lookup_invoice` | none | `payAndConfirm`'s never-false-failure race can't verify an indeterminate outcome — `ok`/GFY *are* authoritative, but a timeout must say "unknown, check ShockWallet" rather than pretend |
| 23196 notifications | none | No live refresh; poll nothing, since there is nothing to poll |
| `pay_keysend` | none | Podcasting 2.0 boosts unavailable on that connection |

None of those are fatal — a Debits connection is a **spend surface**, and Sidecar
already knows how to be honest about what a wallet can't do — but they are the
product question: the Wallet tab for a Pub user becomes "pay from your Pub," not
"your Pub, in a panel." Worth deciding before building, not after.

### 3. Native lightning.pub RPC (kind 21000) as a full backend — hold

A full wallet: balance, history, invoices, pay — the ShockWallet protocol itself.
Held for three reasons: it is one vendor's fast-moving autogenerated surface (100+
methods) rather than a standard; its transport encrypts with **NIP-44 v1**, a
superseded draft — the vendored `nostr-tools.js` implements v2 only — so a signer
would hand-roll legacy conversation-key crypto to speak it; and even then it buys no
lightning address the operator hasn't configured by hand. Reopen if ShockNet standardizes an
account-info subset into CLINK — at which point option 2 grows a balance query for
free — or ships NIP-47, at which point option 1 subsumes everything.

### 4. Enroll quick start — Rizful-shaped, and held by the standing constraint

Kind **21004** provisions the sending key as an account on any Pub and returns
`{noffer, ndebit, nmanage}` — "direct-use only," no third-party grants — with
optional NIP-13 PoW whose difficulty a Beacon (`d=clink-node`, 30078) publishes. It
is the Rizful quick start without the custodian: paste a friend's nprofile, get an
account, auto-allowed debits, a noffer for your profile. Held because:

- **No lud16 comes back.** Enroll returns no lightning address, and `bridgelet` is
  static config with no self-service registration — so a Sidecar-enrolled account
  has no zap button in every mainstream client, which is the disqualifying row of
  the table at the top of `WALLET_BACKENDS.md`. Only CLINK-aware clients (Zeus,
  ShockWallet, Amethyst, bxrd) could zap the noffer.
- No balance or history without option 3, so the account is spend-and-receive
  blind.
- **The key question has only bad answers today.** Enroll with the identity nsec
  and the nsec becomes a bearer instrument for money — verbatim the recorded
  objection to NIP-60. Enroll with a separate key and there is a second
  money-adjacent secret to back up, invisible to ShockWallet, in a product whose
  backup story is built around exactly one secret.

Reopen when: Enroll or bridgelet can hand back a self-service lightning address;
CLINK grows an account-info query; and the project has decided how many secrets the
backup story may carry.

## Payer polish that stands on its own

Whatever is decided above, these are small, shipped-quality fixes to code that is
already in the tree:

1. **Zaps to a noffer are not zaps.** When a profile has an offer and no lightning
   address, the bolt opens the offer panel (`offerFound`,
   `sidepanel.js` ~2935) — but `clink.js` sends no `zap` payload, and the spec says
   requests to a `zap_*` offer without one "are treated as spontaneous payments."
   Sats arrive; no kind 9734 is committed, no 9735 receipt lands on Nostr; the
   recipient's client shows nothing. Sidecar already builds and signs kind 9734 for
   the LNURL zap path (`zapInvoice` in the panel), and already discloses exactly this
   nuance on the comment-zap QR handoff ("sends a payment to the author, not a zap
   on this comment"). Send the `zap` payload (and `payer_data`), and say so on the
   handoff.
2. **Moved offers.** Error code 3 may carry `latest` — a fresh `noffer1…`. Accept
   it, retry once against it, and never silently rewrite the stranger's profile.
3. **Beacon pre-flight (optional).** One subscription on the offer's relay for a
   fresh (≤180s) `d=clink-node` beacon turns a 30-second "the offer did not answer"
   into an immediate "its wallet is offline," and `serviceFeeFloor`/`serviceFeeBps`
   give the payer a fee disclosure before the ask rather than after it.
4. **Ledger corrections.** `clink.js`'s header still cites the closed NIP PR as
   live; and `WALLET_BACKENDS.md`'s CLINK entry says "Still held … Cheap to add
   alongside NWC once that changes" while Offers shipped in #359 and Debits is
   assessed above. Correct the entries rather than argue with them — this document
   is the assessment to fold in.

## Upstream asks, in order of value to Sidecar

1. **NIP-47 shim on lightning.pub.** Ask once, in their issue tracker, with the
   use case (every NWC-native client works unchanged); accept the likely no.
2. **Debit retry semantics.** After a timeout, is resending the same `bolt11`
   idempotent (same invoice, so LN settles it at most once — but does the service
   return the stored result or a duplicate failure)? This is what lets Sidecar keep
   something like its never-false-failure contract without `lookup_invoice`.
3. **A lightning address from Enroll**, or self-service bridgelet registration.
4. **clinkme.dev listing** bumped to Offers + Debits when/if it ships.

## What would change the answer

- lightning.pub ships NIP-47 → option 1, done; a `wallets.js` entry and a
  changelog line.
- CLINK grows an account-info/balance query → option 2 stops being spend-only and
  becomes a real second backend; option 4 loses its blindness.
- A mainstream Nostr client draws zap buttons from a profile noffer the way it does
  from a lud16 → the standing constraint dissolves, and the Enroll quick start
  becomes the best onboarding story Sidecar has ever had: paste a friend's
  nprofile, receive a working wallet.

One hands-on check remains before any of this is built: where in wallet2's UI a
user actually finds their `ndebit1…` to paste. The spec and SDK define the string;
the repo's README does not show the screen. Verify in the app (or the
[clink-demo](https://github.com/shocknet/clink-demo) playground) before writing
connect copy that promises it.
